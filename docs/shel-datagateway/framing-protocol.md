# TF-Server Framing Protocol Specification

> Source: `TF-Server Framing Protocol Specification.pdf`, 16 Apr 2026.
> Confluence: https://trillium.atlassian.net/wiki/spaces/TF/pages/1821147191 (access required)

Defines the transport used by backend services: **SHELDataEngine**,
**JournalWriter**, **JournalReader**. The protocol is independent of the
application-level message protocol it envelops.

## At a high level

- **TCP** as transport, a single connection carrying many streams.
- **Client → Server**: newline-terminated JSON objects (NDJSON / JSONLines).
- **Server → Client**: binary **frames**, identified by request id, multiplexed.
  Each frame is a binary header followed by its payload.
- Payloads may be compressed.

## Terminology

| Term | Meaning |
| --- | --- |
| **Stream** | A unidirectional flow of bytes from server to client, carrying one or more messages. |
| **Message** | A logical communication unit defined by an external protocol — application- and possibly request-specific. The framing layer is agnostic to it. |
| **Frame** | The smallest unit of communication. Carries a header that at minimum identifies the stream (and so the request) it belongs to. |

## Client → Server

A single stream of JSON request objects, serialized one per line
(NDJSON/JSONLines). Each request object **must** contain an integer field `id`,
unique for the TCP session. All other fields are application-specific.

## Server → Client

The response to each request forms a **separate stream**, uniquely identified by
the Request ID. Frames from different streams are **interleaved (multiplexed)**
and reassembled client-side via the Request ID on each frame.

Consequence: requests do not block each other, so long-running live
subscriptions can share one TCP connection with historical requests.

### Frame Header

All integer fields are **big-endian**.

| Field | Length (bytes) | Type | Description |
| --- | ---: | --- | --- |
| Request ID | 4 | Integer | Identifies the request |
| Payload Size | 4 | Integer | Size of payload in bytes |
| Flags | 1 | Bitmask | See Flags below |
| Status Code | 1 | Integer | If the 'End of request' flag is not set, value is 0. See Status Code below. |
| Uncompressed Size | 0 or 4 | Integer | **Optional** — present only if the 'Compressed' flag is set |

**Header size is 10 bytes normally, 14 bytes when the Compressed flag is set.**
Parse Flags before deciding how many bytes to consume.

### Flags

| Bit | Name | Description |
| --- | --- | --- |
| `0x01` | End of request | Indicates the end of the reply for this request id |
| `0x02` | Server response | The payload is an out-of-band message generated by the server |
| `0x04` | Compressed | The payload is compressed; `Uncompressed Size` is present to aid memory allocation |

> **Conflict — compression algorithm.** The protocol overview states ZSTD. The
> formal spec says: *"The compression protocol utilized is not explicitly
> defined. The client must make assumptions. This is to be tackled as a future
> improvement."* Treat ZSTD as the working assumption but do not hard-code it
> without confirming against a live frame.

### Status Code

Only meaningful when the **End of Request** flag is set.

| Code | Description |
| ---: | --- |
| 0 | No error |
| 1 | Resource not found |
| 2 | Other Error |

## Request Lifetime

- A **historical / closed-ended** request sets the *End of request* flag to
  signify completion. The stream then closes; no further frames arrive for that
  Request ID.
- A **live / open-ended** request simply never sends a frame with *End of
  request* set. It acts as a subscription to live data.

### Cancelling

The client can terminate any active request, open- or closed-ended, at any time:

```json
{
  "id":                <integer>,
  "action":            "cancel",
  "target-request-id": <integer>
}
```

The response stream to the cancel request **always returns with no error**, even
if the target request completed naturally before the cancel was processed.

If the target request is terminated by the cancel, it sends a final frame with
the *End of Request* flag set and **Status Code 2 (Other Error)**, with the body
containing type `"CANCELED"`.

> Note the asymmetry: a successful cancel surfaces as an *error* status on the
> cancelled stream, not a clean close. Don't treat status 2 as a failure without
> checking whether the body type is `CANCELED`.

## Out Of Band Messages

Signalled by the **Server response** (`0x02`) flag.

### Control Messages

Can appear mid-stream; meaning is defined at the application level. Example —
the point where a stream switches from rewind to live data:

```json
{
  "category": "control",
  "type":     "end-of-rewind"
}
```

### Error Messages

When Status Code reports an error, the server may send additional detail as
out-of-band data:

```json
{
  "category": "error",
  "type":     "RESOURCE_NOT_FOUND",
  "message":  "free-form error message"
}
```

Known `type` values: `RESOURCE_NOT_FOUND`, `VALIDATION_ERROR`,
`RATE_LIMIT_ERROR`, `INTERNAL_ERROR`, `CANCELED`, `UNKNOWN_ERROR`,
`SERVICE_UNAVAILABLE`.

The spec notes that not all errors can be enumerated in the header's Status
Code, and that framing-level ones like `CANCELED` are candidates for promotion
into it. So **do not assume the Status Code enum is stable** — always read the
out-of-band body.
